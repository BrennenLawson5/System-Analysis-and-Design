# System-Analysis-and-Design

The DriverPass Project was all about designing a system for DriverPass, a company that provides driver training services. They wanted me to design a web-based scheduling and training platform that supports multiple different users (customer, staff, IT admin, owner). 

I feel that with this whole project, I did a good job figuring out what exactly the client was asking for, and then laying out what was needed in order for these requests to be fulfilled. When you have a client that isn't technical and they give you basic requests, it takes a lot of time and researching to figure out exactly what is needed for the system to work in the way they are wanting it to work. 

If there is one thing about this project that I would like to improve, it would be my diagrams. I'm not crazy about using LucidChart and a lot of the times, I get frustrated with it, but if I spent more time with it, maybe I would be better at making the diagrams. 

Interpreting the user's needs can be tricky, but one way I did that was by reminding myself of the core features and attributes of the system that the client really emphasized. Considering the users needs is very important, because a system can work and be "technically correct" but also fail if it is confusing, slow, and/or doesn't match how people really work. 

My approach to designing software is to start out broad with the core features and mechanisms of the system, and as time goes on and the project progresses, then start tightening the design and narrowing down what should really be in it. In the future, I would use a lot of the same strategies that we used for this project, like requirements breakdowns, user stories, and iterative modeling.
